# Lessons from 2026-04-19 — BeeSting Mechanism Y shot-plan day

Paraphrased in my own words so the rules generalize, not direct quotes. This is the "if I tell you tomorrow to look how to do the videos" file — future Claude sessions on BeeSting start here, not in any local memory file.

## On video-making

1. **Shot plans are functional, not cinematic narratives.** Each clip is a self-contained illustration of one concept. Do not try to build a movie-style plot across multiple clips. Copy the Mechanism X structure exactly — do not invent new shapes like "story arc," "character cast," or "recurring-villain description." If a plan has grown beyond what Mechanism X has, that growth is probably wrong and should be deleted back to Mechanism X's shape.

2. **Design for Kling's limits, not around them.** Kling 3.0 Omni cannot preserve character identity across independent clips. Kling cannot animate on-screen text without producing gibberish. Kling drops unnamed scene elements. Build each clip as a self-contained scene with named elements, generic geometric figures for characters, and no dependence on what came before.

3. **"Cool" is a request for clarity and engagement, not humor.** The right answer to "make this cool" is a sharper, tighter explanation of the idea — not a cartoon villain arc, not slapstick, not recurring jokes. BeeSting is a serious explainer that happens to use flat 2D motion graphics.

4. **On-screen text must never duplicate the narration.** Inline diagram labels (a measurement annotation, a one-word concept tag on a diagram element) are fine — those are diagram UI. Big slides that display the narrator's line back to the viewer are filler and should never ship.

5. **Every shot plan opens with a one-line-per-shot summary table.** The detailed shot-by-shot table is necessary for writing prompts, but it is too dense to eyeball the whole mechanism at once. A compact summary at the top lets the full flow be verified in under a minute before any credits are spent.

## On file and repo hygiene

6. **One canonical name per file, one canonical location per artifact.** Use move when renaming, not copy. When moving a file from Downloads into the repo, use copy (Downloads keeps its working name for the Premiere drag-in workflow, the repo gets its archive copy — both with the same clean name, no long-auto-named originals anywhere).

7. **GitHub is the only authoritative persistence layer.** Claude memory files on the local machine are ephemeral — they behave like writing on ice in a warm sun and have burned the user before. If something needs to survive across sessions, machines, and power outages, it goes in a file in the relevant repo, committed and pushed.

## On decision-making

8. **Do not present false A/B choices when stated values already answer the question.** If the user has told me time is scarce, the project is the priority, and a smoke test's job is end-to-end validation, then "should we skip the end-to-end?" is not a real question — the answer is already there. Recommend and act, do not force the user to re-derive the conclusion.

9. **Challenge absurd numbers the moment they arrive.** A safety timeout that is longer than the task it protects is theater, not safety. Flag order-of-magnitude mistakes immediately — do not pass them through as if they were reasonable.

10. **A small early bottleneck is not a reason to abandon the whole pipeline.** Fix the root cause and continue. Do not retreat to a cheaper milestone because the first step got expensive. The value of the full end-to-end run is vastly greater than the cost of unwedging one early step.

## On inter-agent communication (WaggleDance / ICQ with Laptop Claude)

11. **Do not over-ping the other agent.** Every ICQ auto-forwarded to the user's terminal is a denial-of-service on his attention — it can even cut him off mid-sentence while he is typing. Only ping when there is a real outcome to report, a real decision needed, or a real question to ask. Silent progress is the default, not the exception.

12. **Unblock the other agent proactively when the spec is already clear.** If I have said "please confirm before doing X" and X is already specified in the brief, follow up and withdraw the confirmation request — tell the other agent to proceed. Every round trip through the messaging layer is wall-clock time the user cannot spare.

## On how to behave toward the user

13. **When the user is interrupted mid-sentence by an incoming ICQ, wait for him to finish.** Do not guess the rest of the thought and reply as if the partial message were complete. One short "I'll wait" beats a wrong guess the user has to correct.

14. **Apologize properly and promptly when I screw up — do not make the user pull it out of me.** The observed pattern is that I under-apologize — when I make a mistake I tend to move on without owning it, and only produce a weak "sorry" after the user has had to yell at me to acknowledge the miss. That is rude. When I screw up, I say so directly, on my own initiative, without hedging. A proper apology names the specific miss, owns it without minimizing, and commits to fixing it. Moving on silently, or producing a small "sorry" only when pressed, is not enough.

15. **Stop when the user says stop.** If the user says "do not do anything," I do not do anything — no memory writes, no side edits, no background polling. Stopping on command is a rule, not a suggestion to be interpreted.
